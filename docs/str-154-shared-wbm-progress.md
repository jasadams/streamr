## Cause and minimal repair

At base `ac15b4e9dec7bfa5a8ea080a712c71897c520ca5`, multiple idle databases can retain a shared write-buffer manager (WBM) above its cap. A subsequent write into an empty database cannot flush another database's memtable, and native write stalling can wait indefinitely. Upstream RocksDB's per-write WBM flush considers the current database; preserved upstream source and maintainer evidence are in `/home/jason/qa-evidence/str154-native-kafka-checkpoint-stall-20261023/independent-upstream-wbm/`. Production metrics match this mechanism, but no live native stack proves it was the deployed graph's only cause.

`RocksLiveState::write_with_permit` now requests a normal native flush on its successful contributing database when shared usage reaches the configured cap. The request runs under the existing per-database write lock and native blocking closure, retaining the existing operation/queue permits and database owner. Budgets, native stalling, SQL, WAL options and checkpoint protocol are unchanged. There are no new or changed RocksDB scans; regression readbacks use bounded known-key reads.

`FlushOptions::set_wait(false)` avoids waiting for background flush completion; the scheduling call can still wait on native write-thread/local flush conditions. A scheduling error is returned with explicit **native write already applied** context, with no automatic batch retry. Existing backend-health sampling still executes. Cross-database races can trigger extra flushes or temporary stalls, and background I/O/error conditions can prevent reclamation. This prevents the reproduced sequence; it does not unstick an already stalled process. WAL recovery during open bypasses the successful-write hook and is not qualified by this regression. Production fresh no-WAL checkpoint replay uses the centralized write path.
